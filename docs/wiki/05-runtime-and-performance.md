# 05 · 运行时与性能

[返回目录](README.md) · [上一页：清算风险](04-clearing-and-risk.md) · [下一页：UI](06-ui.md)

> 本页全部性能指标都是设计预算，尚未运行新引擎基准测试。不能据此承诺任何电脑绝不卡顿。

## 1. 部署形态：一个进程内的小型引擎

继续保持 `StardewCapital.Core` 与游戏适配层分离。Core 不依赖 SMAPI、`Game1`、浏览器、网络服务或具体 UI。

```text
StardewCapital.Core
  时间与事件调度
  经济状态与信息发布
  智能体策略
  交易所与订单簿
  账户、清算、风险
  公共快照、诊断、存档

独立模拟宿主 / 游戏适配器
  提供时间、用户命令、存取款和库存桥接
  接收只读快照与事件

玩家终端 / 开发者观察台
  展示快照，提交命令
  不直接改账户、持仓或行情
```

这些首先是逻辑模块，不要求立即拆成很多项目，更不要求微服务。第一版一个单线程确定性事件循环足够作为起点；只有基准测试证明需要时才增加线程。

## 2. 一条权威模拟时钟

内部使用绝对游戏时间，例如从第 1 年第 1 天开始累计的游戏分钟，加同一时刻的事件序号。年份、季节、日和 `HHMM` 只是展示/适配形式。

不要直接用 `HHMM` 数值相减算时长。06:50 到 07:10 是 20 分钟，不是 60。旧 `SimulationClock.GetDayProgress()` 直接对 HHMM 做减法，应在迁移时加专门测试并修正。

建议首次配置：每游戏分钟一个市场逻辑步，交易窗口 06:00—22:00，因此每交易日 960 步。这个步长是可调模拟分辨率，不是每秒 60 次渲染，也不是已经选定的真实秒更新频率。

所有到期、订单 TTL、保证金宽限、新闻传播和代理冷却都使用模拟时间。日期跨季、跨年不能让到期合约复活，亦不能让永久新闻重新触发一次。

## 3. 游戏时间、真实时间、绘制时间各管什么

| 时间 | 用途 | 禁止用途 |
|---|---|---|
| 权威游戏/模拟时间 | 决策、到期、新闻、风险、撮合事件顺序 | 被 UI 随意修改 |
| 真实时间 | 测量运行耗时、安排绘制、独立宿主播放速度 | 在游戏暂停时继续偷偷交易 |
| 渲染帧 | 显示已有状态、动画和鼠标反馈 | 每帧重算整个市场 |

独立宿主的 1×/10×/100×是更快地执行相同逻辑步骤，不是减少 NPC 或跳过风险检查。同一输入的最终事件哈希应一致。

游戏适配器只有在确认游戏时间正在合法前进时才发放模拟时间预算。目标版本能提供可靠的分钟内进度时，可平滑驱动；只拿到离散的 10 分钟时间事件时，先正确执行对应逻辑步，并分批处理，不假装拥有精确连续时钟。

不能为了让行情动起来，随意在菜单 `update` 中直接累加 `Game1.timeOfDay`。这可能与原版时钟、其他 Mod 和多人同步冲突。具体非暂停终端方式必须在目标游戏/SMAPI 版本验证；相关事件和上下文接口参见 [来源 R6](09-sources.md)。

## 4. 暂停策略必须明确

- **正式交易终端打开：** 设计目标是不暂停游戏，世界与市场一起前进；采用经过兼容性测试的非阻塞界面/时间适配方案。
- **游戏真正暂停、存读档、切回标题：** 市场也暂停，不积累离线待补交易时间。
- **多人模式：** 后续只由主机掌握权威市场时钟，客户端不各跑一个市场。
- **独立研究沙盒：** 可以暂停看数据，也可单步执行；该能力不等同于正式游戏中的暂停套利。
- **玩家提前睡觉：** 按明确规则补算到收盘，完成日结，再处理夜间经济和新闻。不能直接跳过未完成的强平、到期或挂单事件。

旧版本曾出现过“菜单时间停住但价格继续走”的体验问题；新适配验收必须覆盖这一情境。当前基线仓库未包含完整游戏菜单实现，因此这里规定的是未来适配目标，不宣称已经修复。

## 5. 每一步的确定性处理顺序

建议约定以下阶段，并在保存/回放中固定版本：

```text
1. 处理到时的市场状态与经济事件，发布到时公开的信息
2. 处理已接收的玩家命令、订单失效和必要撤单
3. 唤醒本步到期的代理，使用其合法观察生成意图
4. 按事件时间、阶段和接收序号执行风险预检与撮合
5. 原子应用每笔成交到双方账户、持仓和公共行情
6. 更新风险；安排有界的强平事件
7. 处理到时日结/到期/保存屏障
8. 发布一致的公共快照和必要诊断统计
```

这一顺序不代表玩家天然比所有 NPC 更快。实际命令拥有接收时刻和延迟规则；同一时间的公平排序在规则中固定。不能让按键帧率或数组顺序决定永远谁抢先成交。

成交驱动的下一次策略响应安排在允许的后续时间，不在当前函数里无限递归。强平优先级必须公开且确定；如果处置链超出本步预算，保留队列和状态，暂停新增风险并继续处理，不丢事件。

跨多帧执行同一逻辑步时，UI 保留上一份完整快照，新用户命令排队。不能把处理了一半的账本暴露给玩家。

## 6. 事件驱动与不同频率

32 个代理不需要每步全部思考。每个代理保存 `nextWakeAt`，只有到时或遇到相关信息才唤醒。

候选节奏：做市商每 1—3 个游戏分钟或盘口明显改变时；趋势者每 3—10 分钟；价值型每 5—15 分钟或新闻到来时；经营套保者每 15—60 分钟或经营计划改变时。加入小范围抖动，避免所有人整点同步。

这些都是待校准参数。风险检查在成交、标记更新和重要账户事件后进行，不因策略低频而跳过。

多个代理共享只读市场指标缓存：均线、近期 VWAP、波动、盘口深度等增量更新一次，不由每个 NPC 重扫全部历史。

## 7. 性能配置与初始预算

以下是目标规格，不是测试结果。正式记录必须包含 CPU、内存、运行时版本、构建模式、场景、耗时分位数及 GC 分配量。

| 项目 | 首个实验 | 后续默认目标 |
|---|---:|---:|
| 全市场 NPC 数 | 12 | 32 |
| 活跃合约 | 1 | 最多 3 |
| 市场逻辑分辨率 | 1 游戏分钟 | 1 游戏分钟 |
| 每代理每次新增订单上限 | 2 | 2 |
| 全市场活动订单硬上限 | 500 | 2,000 |
| 单一图表可见点数 | 约 600 | 约 1,000 |
| UI 数据快照刷新 | 2—4 次/真实秒 | 2—4 次/真实秒 |
| 常态 Core 内存预算 | 小于 50 MB | 小于 100 MB |
| 普通逻辑步目标 | P95 小于 2 ms，P99 小于 5 ms | 同左，需实测 |

Core 内存不含原版游戏、图形资源和开发工具。目标测试至少包括无独显普通笔记本与开发机；不能只在开发机上通过就声称低配支持。

嵌入游戏时再限制每帧主线程模拟切片，例如约 1 ms 的目标预算；必要时分帧处理步骤。时间预算不是允许忽略账本正确性的借口。

活动订单上限应有每账户配额及风险处置预留，避免一个账户占满整个交易所。达到上限时拒绝新增长风险订单、允许撤单和受控减仓，不静默删除有效挂单。

## 8. 与显示无关的复杂度控制

**不采用“正在看的商品精细模拟，不看的商品换一个价格公式”。** 玩家持仓和未成交订单所在市场必须保持相同撮合与风险规则。

允许的优化：降低不可见图表刷新；缓存盘口聚合；对真正没有活动合约、订单和持仓的经济品种低频更新；按固定配置使用更少 NPC；对未来尚未挂牌合约不维护订单簿。

任何改变模拟密度的模式应在新实验/明确安全边界选择，并写入配置哈希。不能根据运行时帧率偷偷切换经济规则，否则不同电脑会得到不同结果。

超预算处理顺序：先减少日志与绘制，再缓存统计、消除分配、分帧消化队列；仍不足时在安全边界提示使用低负载预设。风险与结算事件不可丢弃。持续积压时进入清楚可见的“同步中/暂停新增风险”，而不是让撮合落后、UI 却宣称已成交。

## 9. 订单簿的数据结构不必一步到位

当前列表实现可作为小规模验证基础，但需要保证同价 FIFO，并测量复制、排序和查询开销。订单量扩大后，可改为有序价位集合 + 每档 FIFO 队列 + 订单 ID 索引。

不要先实现复杂的高频交易基础设施。只有配置上限内的基准显示列表成为瓶颈时，再替换底层结构，并用相同测试确认行为不变。

历史使用有界缓冲：保留必要近期逐笔、完整日线与压缩摘要。开发模式可输出完整事件日志到文件，但不是默认每帧 JSON 序列化整个世界。

## 10. 存档必须保存整个市场，不只是价格

至少保存：规则/存档版本、配置哈希、绝对时钟、下一事件序号、合约状态、账户与账本游标、持仓及成本基准、未成交订单和 FIFO 顺序、预留资金、代理状态、待处理事件、已触发事件实例、随机流状态、指数与风险标记、日结/到期进度。

每个子系统使用独立可复现随机流；渲染不消耗市场随机数。选定并版本化随机算法，避免运行时升级后默认随机实现变化导致回放漂移。

在一致性屏障原子保存，保存失败保留旧完整版本；恢复后不能重复结算、重复发布事件或重置订单优先级。迁移失败应拒绝加载并给出原因，不能悄悄把账户清零。

Core 存档与游戏金币/库存转移需要事务 ID 和幂等协调。存款已从游戏钱包扣除、Core 尚未保存的故障情境必须测试；否则玩家可能丢钱或复制金币。

## 11. 运行验证

同一种子、配置和命令日志在以下条件下应给出相同结果：无 UI；打开 UI；切换图表；不同绘制帧率；加速回放；中途保存再恢复。多线程浮点计算与现实时间戳不能破坏这一契约。

性能测试至少覆盖：平静交易、新闻同时唤醒、挂单上限、跨多档扫单、连续保证金处置、到期日、提前睡觉补算和长时间运行。报告 P50/P95/P99、最大切片、分配量、内存趋势和待处理事件峰值。

正确性通过后再谈“更真实”；性能通过后再扩大市场。规则型多智能体是可行的轻量设计方向，但实际开销必须由这些测试证明。
