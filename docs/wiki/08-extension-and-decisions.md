# 08 · 扩展基础与决策记录

[返回目录](README.md) · [上一页：路线与验收](07-roadmap-and-tests.md) · [下一页：来源与术语](09-sources.md)

## 1. 为什么从期货开始仍然能为其他市场打底

真正可复用的是身份、资金、订单、成交、持仓、事件、时间、信息、风险接口和观察工具。不是让所有资产都套用同一条价格公式，也不是把“期货合约”改一个名字就当股票。

期货阶段的投资重点应该是：每笔交易可对账、每种资产有明确规则、经济活动可以影响参与者判断、不同前端可以调用同一个引擎。

## 2. 核心与资产规则的边界

| 共享核心 | 资产专属规则 |
|---|---|
| 实体、账户、币种、时间、事件 ID | 发行、到期、分红、赎回与交割 |
| 限价簿、撮合、公平顺序、撤单、成交日志 | 是否允许做空、杠杆与融资要求 |
| 账本、资金预留、幂等转账、持仓登记 | 资金/实物交换和日结方法 |
| 公共信息、代理观察、研究诊断 | 基本面来源与特定风险因子 |
| UI 命令/快照与历史查询 | 合约字段、特定提醒和账单解释 |

建议保留少量清晰能力边界，例如 `InstrumentSpec`、`AccountLedger`、`MatchingVenue`、`RiskPolicy`、`SettlementPolicy`、`ValuationProvider`、`CorporateActionHandler`。

这些名字是设计建议，不是当前已经存在的接口。第一版先实现期货所需最小能力，不提前创建几十个空接口。

特别注意：`ValuationProvider` 给估值与风险参考，不拥有改写成交价的权限；`SettlementPolicy` 可以结转账户，但不能伪造成交。

## 3. 一套实体身份贯穿经营与金融

未来的皮埃尔商店可以是一个 `Entity`，有经营资产、库存、现金、债务和所有权。它参与商品交易的代理、购买期货的代理和管理贷款的逻辑，都使用同一实体的真实资源。

```text
实体
 ├─ 经营：生产、库存、采购、销售
 ├─ 资产负债：现金、应收、贷款、股本等
 ├─ 账户：不同币种与交易用途
 ├─ 策略：套保、投资、资金管理
 └─ 发行资产：公司股票、将来可能的债券
```

不能给同一家商店的经营系统、期货系统和股票系统各发一份独立无限钱包。玩家经营行为改变企业财务，再影响公开信息和交易者估值，最终通过订单影响资产价格。

## 4. 股票：从一家公司做起

建议先实现一家拥有简单经营账本的商店，以及一类普通股：收入、成本、现金、债务、发行股数、股东持有量、公开经营报告和基础分红事件。

股票初次发行必须有股份登记与认购资金流；二级买卖由买方支付资金并取得股份，卖方交出股份并获得资金。首版股票可先禁止裸卖空，避免提前引入证券借贷。

股价由参与者根据公开利润、资产、增长和风险下单形成。不能“利润上涨 10% → 系统直接把股价上涨 10%”。盈利企业也可能估值下跌，因为预期、流动性和风险发生变化。

重要区别：期货所有账户净头寸之和为零；股票持有量之和对应合法发行且登记的股份数量。不能把期货的零和持仓不变量直接套到股票上。

拆股、增发、分红、退市、破产是公司行动和账本事件，不是图表特效。第一家股票稳定后再增加其他商店。

## 5. 外汇：先把币种账本做对

现在的金额结构就应包含 `CurrencyId`，即使第一版只有 g。不要把全系统写死为无币种 `double Balance`。

后续现货外汇成交是两种币的对向交换：买方付出报价币、取得基础币，对方反向变化。两条资金腿应作为一个原子事件记账；手续费币种和汇率报价方向必须明确。

第一版外汇可只做无杠杆兑换与跨地区贸易需求。不同货币的余额不能直接相加；账户总值是基于指定参考汇率的估值，不是现金已经兑换完成。

贸易、资本流动、政策与资金需求影响参与者下单。中央银行未来可以通过正式交易进行干预，但不应绕过订单簿直接设置所有汇率成交。

运输与地区差价不必自动等于外汇。只有世界确实定义了不同货币和结算需要，才引入该市场，避免凭空增加一套无经济用途的价格。

## 6. 基金：先是持仓组合，再考虑交易所价格

基金应持有真实资产和现金，并发行明确份额。净值来自资产估值减负债，再除以份额；费用、申购、赎回和持仓变化都能对账。不能另外生成一条随机基金收益曲线。

先做简单开放式组合：按已公布的净值规则进行申购赎回，明确截止时间、估值时间和费用。它不必使用股票式订单簿。

只有将来引入交易所交易的基金份额时，才同时存在二级成交价与基金净值，并研究溢折价及申赎约束。不要把净值当作任何时刻、任何数量都保证可成交的价格。

期货持仓的基金还需处理保证金、展期和现金流，不是简单把几条期货价格取平均。

## 7. 银行与中央银行：最后接入的是资产负债关系

初期把利率、融资成本和汇率参考定义为外部可配置服务即可，不为了期货估值先实现完整货币体系。

后续商业银行必须记录贷款、存款、利息、资本、准备金/流动性和违约。贷款不能同时成为借款人和银行的无条件净财富；需要有对应资产、负债与信用风险。

本项目若选择允许贷款创造存款，应把这种货币扩张定义为显式双重记账事件，并设置资本与流动性约束；此时“全经济现金总量永远固定”不再是正确的不变量，但资产负债和交易对账仍需成立。不要把期货封闭实验的资金守恒检查原封不动套到所有宏观机制上。

中央银行可通过政策利率、流动性工具和正式资产交易影响银行与市场；作用链应是：政策 → 账户约束/融资条件/预期 → 行为 → 成交，而不是“加息按钮让全部股票乘以 0.9”。

未来的货币规则需要单独研究与验证。本 Wiki 只规定扩展边界，不宣称已经建立完整宏观经济模型。

## 8. 最小外部调用面

独立宿主和星露谷适配层围绕以下语义工作：

```text
提交命令：下单、撤单、授权转账、经营/库存事件
推进时间：推进到某个合法的绝对模拟时刻
读取公开快照：行情、规则、已公开新闻
读取本账户快照：资金、订单、持仓、风险、账单
保存/恢复：一致性快照、版本与事务游标
研究接口：显式授权的完整诊断与回放
```

游戏代码不能直接修改内部字典；UI 不能直接调用代理决策；价格图不能反向决定市场趋势。这样独立模拟器、游戏内终端和未来其他前端都能共享规则。

## 9. 决策记录

| ID | 决策 | 理由与代价 |
|---|---|---|
| D01 | 独立金融经济核心，游戏只是一个适配端 | 符合长期目标；需要清楚的时间和资源桥接 |
| D02 | 先期货，后其他资产 | 把交易、账户和清算闭环做成可复用基础 |
| D03 | 新模式成交价来自订单簿 | 获得真实交互；代价是必须承担流动性和风险问题 |
| D04 | 基本面与估值不直接指定收盘 | 避免预定路径与玩家交易冲突；不能保证每天“好看” |
| D05 | 规则型、有限规模、单线程优先 | 减少负载和调试成本；不追求研究级高频真实性 |
| D06 | 所有参与者有限资金且使用同一风险规则 | 防止隐藏无限对手盘；允许危机和停市 |
| D07 | 先现金到期，再实物交割 | 先验证清算；阶段性放弃完整期现套利 |
| D08 | 玩家终端和研究观察台分开 | 保持信息规则，同时提供完整调试能力 |
| D09 | 时间、随机流与事件日志可回放 | 让 bug 和策略差异可复现；需要保存更多状态 |
| D10 | 旧模型保留为独立 Legacy 模式 | 保护已有工作和对照价值；不能双重写价 |
| D11 | 性能参数先作为预算，必须实测 | 不根据开发机配置承诺所有机器流畅 |
| D12 | 本轮只提交参考文档 | 不提前改动未完成实现和旧存档 |

D01/D02来自项目方向；其余是本 Wiki 的建议默认方案，未来如改动应新增决策记录，说明原原因、改变理由和迁移影响。

## 10. 留待重启时验证的问题

| 问题 | 当前建议 | 需要的证据 |
|---|---|---|
| 市场规模 | 12 起步、32 为默认目标 | 多种子行为与性能报告 |
| 结算指数 | 先用透明缩减现货模型 | 无前视、可解释、抗操纵测试 |
| 标记算法 | 多来源、质量检查、低置信度限制开仓 | 极端盘口和账户攻击场景 |
| 交易终端是否不暂停游戏 | 作为正式体验目标 | 目标游戏版本、单人/多人/时间 Mod 兼容测试 |
| 动态售价覆盖哪些渠道 | 先定义一个有限量批发渠道 | 无固定价无限套利与库存对账 |
| NPC 长期破产后的市场持续性 | 有限基金与显式新资本，绝不暗中重置 | 多季经营与资金来源审计 |
| 第一个扩展资产 | 一家商店股票 | 企业账本与股权登记已具备 |

这些问题不阻止现在使用文档，但它们必须在相应里程碑前解决。不要把待验证假设写成已完成特性，也不要因为未来宏观系统很大而跳过当前最小闭环。
